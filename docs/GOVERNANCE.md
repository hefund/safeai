# AI 安全治理与发布门禁

## 1. 治理目标

将 AI 安全纳入企业常规风险管理、变更管理、供应商管理和事故响应流程。治理框架参考 NIST AI RMF 的 Govern、Map、Measure、Manage，以及 NIST CSF 2.0 的 Govern、Identify、Protect、Detect、Respond、Recover。

## 2. 建议职责

| 角色 | 主要责任 |
|---|---|
| 业务负责人 | 说明业务目的、影响、用户范围和可接受风险 |
| 数据所有者 | 定义数据分级、访问规则、保留和删除要求 |
| AI 平台负责人 | 负责模型网关、检索链路、连接器和技术配置 |
| 安全负责人 | 定义安全基线、测试要求、风险审查和例外流程 |
| 隐私/法务负责人 | 评估适用法律、合同、个人信息及跨境数据要求 |
| 运维/响应负责人 | 监控、告警、隔离、恢复和演练 |
| 独立评估人员 | 对高风险场景执行独立测试并核验整改证据 |

小型团队可以由同一人承担多个角色，但高风险系统的开发、审批和独立验证应尽可能分离。

## 3. 风险分级建议

| 等级 | 示例 | 最低控制要求 |
|---|---|---|
| L1 低 | 公开信息问答、非敏感文本辅助 | 身份认证、模型白名单、基本日志和测试 |
| L2 中 | 内部业务知识库、一般业务文档 | 文档 ACL、敏感数据控制、提示注入测试、变更回归 |
| L3 高 | 财务、人事、法务、研发机密、并购资料 | 严格隔离、独立安全评估、强化审计和高风险操作审批 |
| L4 极高 | 可付款、交易、删除生产数据或修改关键系统的 Agent | 默认禁止自主执行高影响操作；专项评估、独立授权和受控验证 |

风险分级必须基于业务影响、数据敏感度、外部暴露面、自主性、可逆性和失效后果，不能只根据模型大小判断。

## 4. 发布门禁

生产发布前必须具备：
1. 已登记的系统负责人、业务负责人和数据所有者。
2. 已完成的数据分类、威胁建模和供应商评估。
3. 已验证的服务端授权、租户隔离、日志和密钥管理。
4. 已执行与风险等级匹配的安全测试。
5. 所有高危漏洞已关闭；例外必须经过正式风险接受。
6. 已定义监控、事故响应、回滚和恢复方案。
7. 已归档测试证据、配置版本、审批记录和残余风险。

## 5. 例外管理

每项例外至少记录：
- 控制 ID 和受影响系统；
- 未满足的要求及原因；
- 风险等级、潜在影响和受影响数据；
- 补偿控制；
- 风险接受人；
- 批准日期、到期日期和复审频率；
- 关闭计划和验证证据。

高危越权、敏感数据泄露或未授权高影响执行，不应通过一般例外审批绕过发布门禁。

## 6. 变更触发重新评估

以下变更应触发风险复核，必要时重跑完整安全测试：
- 更换模型、模型版本或供应商；
- 修改系统提示、路由逻辑或检索参数；
- 新增数据源、知识库、租户或连接器；
- 修改 ACL、缓存、记忆或索引管道；
- 新增写入、发送、付款、删除或执行工具；
- 发生安全事件或出现新的高危攻击方法。
